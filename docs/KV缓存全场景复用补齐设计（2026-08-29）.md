# KV 缓存全场景复用补齐设计（2026-08-29）

> 依据：《KV 缓存全场景复用触发规范（正式归档版）》。本设计补齐 llama-harness 中未落地的主动复用场景：**4.1 截断断点驻留、4.2 自动冻结防驱逐、4.5 Tool 链锁定**，以及 **§8 可观测日志**（含 4.4/4.6 前缀判定）。

## 1. 现状差距

| 场景 | 状态 |
|------|------|
| 4.1 截断断点驻留 | ❌ 缺失：截断后直接重发续接体，无快照 save、无「截断待续接」标记 |
| 4.2 空闲冻结防驱逐 | ⚠️ 半实现：Preemptive 机制存在但仅 UI 手动，无按应用类型的自动判定 |
| 4.3 重启/自愈快照复用 | ✅ 已具备（绑定持久化 + 重绑定 restore + 崩溃恢复管道） |
| 4.4 裁剪后前缀增量 | ⚠️ 半实现：同槽路由保证原生前缀匹配最大化，缺前缀一致性判定与日志 |
| 4.5 Tool 链锁定 | ❌ 缺失：无工具链会话识别 |
| 4.6 微调 Prompt 增量 | ✅ 原生能力覆盖，缺观测日志 |
| 4.7 双槽亲和防漂移 | ✅ 已实现 |

## 2. 架构决策

**分布式集成**（跟随现有组件模式）：各场景逻辑落在已有职责组件内，不新建中央管理器。

- `OutputContinuer`：截断检测点回调（onTruncation）
- `SlotAffinity`：自动强占判定 + IsPreemptive 访问器
- `KvCacheManager`：DeleteCache 快照清理
- `SmartScheduler`：编排（截断 save/清理、Tool 链锁定、前缀哈希判定）
- `AppConfig` / `MainForm`：配置与 UI

## 3. 场景设计

### 3.1 §4.1 截断断点驻留复用（最高优先级）

**数据流**：

```
PipeLoop 检测 finish_reason=length（且无 tool_calls）
  → onTruncation 回调：kv.SaveAsync(slot, key)   ← 断点快照落 RAMDisk（抢在续接请求发出前，槽位 KV 仍完整）
  → 标记「截断待续接」：_truncPending.Add(key)
  → 自动续接照常进行（重发续接体到同槽，n_slots 亲和）
  ├─ 续接成功（completed=true）→ _truncPending.Remove + DeleteCache(key)
  │     （槽活 KV 已领先断点，旧快照会回退状态 → 按规范 §6.3 清理过期快照）
  └─ 续接失败/崩溃（completed=false）→ 保留标记 + 快照
        → 下次同 key 请求走现有 rebinding restore 路径（HasCache → RestoreAsync）
        → 或崩溃恢复管道使用
```

**接线**：`HandleStreamAsync` / `PipeLoop` 加可选参数 `Func<Task>? onTruncation`；在 `outcome == Truncated` 分支、构造续接体之前触发。save 失败不阻断续接（try/catch 吞掉，日志记录）。SmartScheduler 传闭包捕获 slot/key/kv。

### 3.2 §4.2 主力会话空闲冻结防驱逐（按应用类型可配置）

- **AppConfig** 新增 `AutoPreemptiveApps`（逗号分隔前缀，默认 `"dsh_agent_global,trae_global"`）
- **SlotAffinity.GetSlot(headers, autoPreemptivePrefixes)**：
  - 新绑定创建时：key 匹配任一前缀 → `Preemptive=true`（自动冻结，暂停 LRU 驱逐）
  - 已有绑定每次访问：匹配前缀 → 强制 `Preemptive=true`（应用类型决定，手动取消无效直到移出集合）
- **UI**：4 个复选框（DSH规则引擎 / WebUI / Trae Work / DSH主Agent），映射前缀 `dsh_rule` / `webui` / `trae_global` / `dsh_agent_global`
- 持久化走现有 slot_bindings.json（preemptive 字段已存在）；配置变更即时生效（scheduler 与 MainForm 共享 AppConfig 实例，每次 GetSlot 从 `_cfg` 读取）

### 3.3 §4.5 Tool 工具链连续会话锁定（Body 启发式逐请求判定）

- **检测**：finalBody 的 messages **最后一条** `role == "tool"` → inToolLoop（agent 框架刚回填 tool_result、等待模型响应 = 循环进行中）。历史中残留的旧 tool 消息不作为依据（循环结束后历史仍含 tool 消息，全量扫描会永久误锁）
- **锁定**：inToolLoop 且 key 已绑定且当前非强占 → `SetPreemptive(key, true)` + `_toolLockedKeys.Add(key)` + `[KV-LOCK]` 日志
- **解锁**：后续请求无工具信号且 key ∈ `_toolLockedKeys` → `SetPreemptive(key, false)` + 移出集合 + `[KV-UNLOCK]` 日志
- **不碰用户手动/自动强占的键**：只对「我们锁的」键解锁（`_toolLockedKeys` 只记录实际执行过 SetPreemptive(true) 的键）

### 3.4 §4.4/§4.6 前缀判定 + §8 可观测日志

- **前缀哈希**：内存字典 `_prefixHashes[key] = SHA256(messages[0..n-1] JSON)`（最新一轮之前的全部上下文）。每次 chat/completions 请求（finalBody，TokenGuard 之后）比对：
  - 一致 → `[KV-HIT] {key}：前缀未变 → 原生 KV 复用（增量 prefill）`
  - 不一致（且曾记录）→ `[KV-MISS] {key}：前缀变更 → 全量重算`
  - TokenGuard 发生裁剪时附加说明（裁剪致结构变更 → 全量重算，对应规范 §4.4 约束条款）
- **restore 后刷新**：rebinding restore 成功 → 覆写 `_prefixHashes[key]` 为当前哈希（避免恢复后首请求误报 MISS）
- **统一日志标记**：`[KV-HIT]` / `[KV-MISS]` / `[KV-SAVE]` / `[KV-RESTORE]` / `[KV-CLEANUP]` / `[KV-LOCK]` / `[KV-UNLOCK]`，支撑命中率统计与故障溯源

## 4. 组件改动清单

| 文件 | 改动 |
|------|------|
| `OutputContinuer.cs` | `HandleStreamAsync` / `PipeLoop` 加可选 `onTruncation` 回调（Truncated 时、续接体构造前触发） |
| `SmartScheduler.cs` | 新增字段 `_truncPending` / `_toolLockedKeys` / `_prefixHashes`；ForwardAsync 编排：截断 save+清理闭包、Tool 链检测/锁定/解锁、前缀哈希判定；`DetectToolLoop` 辅助方法 |
| `SlotAffinity.cs` | `GetSlot` 加 autoPreemptive 前缀参数（新绑定自动强占 + 已有绑定强制升级）；`IsPreemptive(key)` 访问器 |
| `KvCacheManager.cs` | `DeleteCache(key)`（删 .bin + 清索引） |
| `AppConfig.cs` | `AutoPreemptiveApps = "dsh_agent_global,trae_global"` |
| `MainForm.cs` | 4 个应用类型自动强占复选框（WriteConfigToUi / SyncUiToConfig / WireEvents 同步） |

## 5. 明确不做（YAGNI）

- 不新建中央 CachePolicyManager
- 不加 TTL 机制（Tool 链锁定随请求自然开闭）
- 不解析 SSE 响应判定工具循环结束（Body 启发式足够）
- 不改 llama-server 侧行为；不改崩溃恢复管道已完成的逻辑
- 前缀哈希仅内存态（重启后首请求全量重算属预期，restore 路径兜底）
