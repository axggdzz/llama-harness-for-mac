# LlamaHarness 首次请求延迟优化工程执行方案

表格

| 项目     | 内容                                                                                                      |
| -------- | --------------------------------------------------------------------------------------------------------- |
| 文档版本 | v1.1                                                                                                      |

| 适用基线 | LlamaHarness v2.7（git 6ced503）/ llama.cpp b10676                                                        |
| 目标模型 | Qwen3.8-27B-Ridge-3.7bpw（MTP 版）                                                                        |
| 运行环境 | Windows 11 / RTX 3080 20G / 64G DDR4 / 双槽常驻                                                           |
| 核心目标 | 首次请求延迟从 5 分钟级降至秒级；不破坏现有槽位亲和 / 崩溃恢复 / KV 复用机制；全程保留 ≥ 15% 显存安全余量 |

---

## 总体执行原则

2. **优先级从高到低，逐阶段落地**：先做零风险、高收益的修复，再做性能调优，最后做架构级改造。
3. **零理解损失优先**：所有优化不截断上下文、不降低模型能力，通过工程手段而非牺牲效果换速度。
4. **单变量验证**：每阶段只改一组变量，跑完对照验证再进入下一阶段，避免问题混杂无法定位。
5. **显存红线**：任何参数调整后，显存占用峰值不得超过 17GB（20G × 85%），保留至少 15% 安全余量。
6. **可回退**：所有改动均保留回退路径，出现异常可一键还原到基线状态。

---

## 阶段一：核心修复与基线参数校准（🔴 最高优先级，立竿见影）

本阶段改动最小、风险最低、收益最大，核心目标是**让 KV-RESTORE 真正命中**，首次请求从全量 173K prefill 变为增量 prefill。

### 1.1 修复 KV-RESTORE 前缀命中（核心银弹）

#### 改动点

2. **存档时机后移**

   - 操作：将 `KvCacheManager.SaveAsync` 的触发时机，从「启动 restore 后」改为「该 key 首次真实请求 prefill 完成（收到 `total time` 日志）后」。
   - 范围：仅对自动预加载 key（`trae_global`、`dsh_agent_global`）执行；手动创建的会话不触发自动存盘。

3. **前缀稳定化改造**

   - 操作：将 `trae_global` system prompt 中的动态内容（时间戳、会话 ID、动态文件列表）从头部移至消息尾部；头部仅保留固定不变的角色定义、规则、项目地图。
   - 原则：头部固定段越长，restore 命中后增量 prefill 越少。

4. **前缀分歧诊断工具（仅调试期开启）**

   - 操作：新增 `PrefixDiffDiagnoser`，save 时镜像一份 token 序列，restore 未命中时自动输出首个分歧 token 位置与对应 message 索引。
   - 边界：仅诊断模式启用，正式运行关闭，不占用热路径开销。

#### 边界约束

- 仅修改存档时机与 prompt 结构，不改动 llama-server 接口、不改动槽位调度逻辑。
- 镜像 token 文件与 .bin 缓存同目录，失败不阻塞主存盘流程。

#### 验收标准

- ✅ 重启 llama-server + Harness 后，`trae_global` 首次真实请求：

  - `prompt eval tokens` ≤ 4096（增量 prefill）
  - 首次请求 prefill 耗时从 304.8s 降至 ≤ 3s

- ✅ 连续 3 次重启验证，restore 均稳定命中。

---

### 1.2 基线参数校准（P4）

按显存红线调整基础配置，修正不合理的超配，为后续调优打基础。

表格

| 参数               | 现值      | 建议值         | 理由                                                                       | 边界约束                                                   |
| ------------------ | --------- | -------------- | -------------------------------------------------------------------------- | ---------------------------------------------------------- |
| `-c`（上下文长度） | 235930    | 65536          | 230K KV 在 20G 显存必然溢出触发 page-fault，反而拖慢；64K 内可完整驻留显存 | 后续根据 q8_0 测试结果可逐步上调至 131072，严禁超过 131072 |
| `--load-mode`      | mlock     | 保留 mlock     | 全量加载 + 物理内存锁定，无页交换，桌面场景最优                            | 不改动                                                     |
| `--ubatch-size`    | 1024      | 2048           | 提升 prefill 单步并行度，直接拉高吞吐                                      | 显存允许可上 4096，不得超过 `--batch-size`                 |
| `--batch-size`     | 2048      | 8192           | prompt 处理批量上限，配合 ubatch 提升                                      | 不得低于 ubatch 的 2 倍                                    |
| `--cache-type-k/v` | q4_0      | 先保持 q4_0    | 阶段一先不动量化，阶段二再测 q8_0                                          | 阶段二切换前必须核算显存                                   |
| `--kv-unified`     | 关闭      | 开启           | K/V 张量连续存储，提升缓存局部性，NVIDIA 长上下文收益明确                  | 开启后监控显存增量 ≤ 200MB                                 |
| `--flash-attn`     | on        | 保留 on        | prefill 速度核心开关，必开                                                 | 不改动                                                     |
| `--spec-type`      | draft-mtp | 保留 draft-mtp | decode 提速 2~3 倍，首 prefill 开销可忽略                                  | 保留 `--spec-draft-n-max 2`，兼顾双槽稳定性                |
| `--cache-req`      | 默认开启  | 确认开启       | 请求级 KV 前缀复用底层开关，关闭后 restore 完全失效                        | 启动参数显式加上，防止默认变更                             |
| `-t`（CPU 线程）   | 8         | 12 + `-tb`     | prefill 阶段 CPU 分词、调度有辅助加速                                      | 不超过物理核心数                                           |

#### 验收标准

- ✅ 启动后显存峰值 ≤ 16.5GB，余量 ≥ 17.5%，符合 15% 红线。
- ✅ 双槽待机稳定，无异常 OOM、无静默 page-fault。

## 阶段二：Prefill 吞吐性能调优（🟠 中优先级，兜底优化）

本阶段目标：**即使 restore 未命中，全量 prefill 时间也减半**。在阶段一验证通过后执行，采用单变量 A/B 测试。

### 2.1 调优步骤（严格按顺序）

2. **第一步：拉满 ubatch**

   - 保持 `q4_0` 不变，`--ubatch-size` 从 2048 逐步调到 4096；
   - 跑 173K 全量 prefill，记录 tok/s 与显存峰值。

3. **第二步：切换 KV 量化为 q8_0**

   - `--cache-type-k/v q8_0`，配合 `-c 65536`；
   - 核算：权重～12.4GB + q8_0 KV ~4GB = 合计～16.4GB，余量 3.6GB（18%），符合红线。
   - 跑同样 173K 全量 prefill，记录 tok/s 衰减曲线。

4. **第三步：上下文扩容验证（可选）**

   - 若 q8_0 + 64K 显存余量充足，逐步把 `-c` 上调到 98304 / 131072；
   - 每档都验证显存峰值不超 17GB。

### 2.2 测试矩阵

表格

| 测试组           | ubatch | KV 量化 | 上下文 | 预期吞吐                 |
| ---------------- | ------ | ------- | ------ | ------------------------ |
| 基线组（阶段一） | 2048   | q4_0    | 65536  | ~570 tok/s 衰减          |
| 组 1             | 4096   | q4_0    | 65536  | ~800+ tok/s              |
| 组 2             | 4096   | q8_0    | 65536  | ~1000+ tok/s，衰减更平缓 |
| 组 3（可选）     | 4096   | q8_0    | 131072 | 验证显存与长上下文吞吐   |

### 2.3 验收标准

- ✅ 全量 173K prefill 平均吞吐 ≥ 900 tok/s，总耗时从 304.8s 降至 ≤ 190s（减半目标）。
- ✅ 长上下文吞吐衰减曲线平缓，尾部不低于 600 tok/s。
- ✅ 全程显存峰值 ≤ 17GB，15% 余量不突破。

## 阶段三：可观测体系与启动流程完善（🟢 低优先级，工程化加固）

本阶段不直接提升速度，核心目标是**把 restore 命中率从不可见变成可量化、可告警、可对账**。

### 3.1 Restore 命中率可观测体系

#### 改动点

2. **真值源切换**：弃用 wrapper 轻量指纹判定，以 llama-server `print_timing` 的 `prompt eval tokens` 作为命中判定唯一标准。

3. **指标落地**：

   - 新增 `RestoreStats` 计数模块：按 key 统计尝试次数、命中次数、误报率、增量 prefill 均值；
   - 持久化到 `config/restore_stats.json`，原子写不丢数据；
   - UI 新增「Restore 命中率」卡片，展示总命中率、单 key 命中率、误报率、最近一次明细。

4. **告警规则**：

   - 命中率 < 80% → 黄色预警；
   - 命中率 < 50% → 红色告警，写入 warn_error.log。

#### 判定规则（与底层日志对齐）

表格

| 场景                          | 判定         | 计入               |
| ----------------------------- | ------------ | ------------------ |
| prompt eval tokens ≤ 4096     | 命中         | hits               |
| prompt eval tokens ≥ 全量 50% | 未命中       | misses             |
| 中间态                        | 保守算未命中 | misses             |
| wrapper 报 MISS + 实际命中    | 真实命中     | hits + false_miss  |
| wrapper 报 HIT + 实际未命中   | 真实未命中   | misses + false_hit |

#### 验收标准

- ✅ 可实时查看 restore 命中率，数值与 llama-server 日志一致，误报率趋近 0。
- ✅ 命中率跌破阈值时，UI 与日志同步告警。

---

### 3.2 启动 Warmup 阶段注入

#### 改动点

2. `SmartScheduler` 新增 `Warming` 子状态：启动后先执行 eager restore + 可选 dummy 预热，完成后再转入 `Running`。
3. 预热期内首请求自动排队，不提前触发全量 prefill。
4. dummy 预热：restore 完成后发一次 `max_tokens=1` 的空请求，捕获 decode graph（边际收益）。

#### 验收标准

- ✅ 启动流程状态可观测：`Starting → Warming → Running`。
- ✅ 预热期请求不丢失、不触发全量重算。

---

### 3.3 日志标准化

#### 改动点

2. slot.log 新增统一标记：

   ```
   [KV-RESTORE-JUDGE] key=xxx hit=1 reason=HitByDelta prompt_eval=656 saved_n=171200 wrapper_hit=0 false_miss=1
   ```

3. 过滤 llama.cpp 已知日志噪声：`model has unused tensor blk.64.*` 警告不进入告警流，仅写入 debug 日志。

#### 验收标准

- ✅ 所有 KV 相关事件可通过关键字统一检索。
- ✅ 已知良性警告不触发误告警。

## 阶段四：中长期治本优化（🟡 中长期优先级，根治大上下文）

本阶段改动最大，从根源压缩 prefill 量，建议前三阶段稳定后再评估落地。

### 4.1 方案选型

**目标**：首请求 prefill 从 173K 降到 10~30K，彻底解决首请求慢问题。
**方案**：放弃全量 codebase dump，改用「本地向量检索 + 按需注入」。

表格

| 方案                                              | 优点                         | 缺点                     |
| ------------------------------------------------- | ---------------------------- | ------------------------ |
| 本地 embedding + 本地向量库（bge-m3 + LanceDB）   | 全本地化、隐私可控、灵活度高 | 需要额外开发检索注入模块 |
| 切换支持本地 codebase 的客户端（如 Continue.dev） | 开发量小，生态成熟           | 更换客户端有迁移成本     |

### 4.2 实施路径

2. 先验证：固定前缀（system + 核心规则 + 项目地图）常驻 KV，走 restore 命中；
3. 代码文件通过检索按需注入，每次请求只注入相关的 10~20 个文件；
4. 与 P0 叠加：稳定前缀常驻 + 变动部分检索，实现全场景秒级首请求。

### 4.3 验收标准

- ✅ 普通编码任务首请求 prefill ≤ 30K token，耗时 ≤ 10s。
- ✅ 代码理解质量不低于全量 dump 方案。

## 风险与回退策略

表格

| 阶段   | 风险                         | 回退操作                                    |

| 阶段一 | restore 命中不稳定、前缀漂移 | 还原存档时机为原逻辑；prompt 结构改回原样   |

## 注意事项

2. **MTP 相关**：不建议关闭 draft-mtp，关闭后 decode 速度会从 44~50 tok/s 跌到 15 tok/s 左右，得不偿失；`blk.64 unused tensor` 为已知日志打印 bug，不影响功能与性能，直接过滤即可。
3. **显存优先原则**：所有参数调整以 15% 余量为红线，宁可降一点上下文，也不要让 KV 溢出到系统内存触发 page-fault，反而更慢。
4. **graph 预热误区**：不要指望预加载 graph 解决首次慢问题，瓶颈在 prefill 算力与 KV 命中，graph 只节省 μs 级 kernel 启动开销，对 5 分钟级延迟基本无效。
5. **单变量测试**：调参时每次只改一个参数，跑同样的 prompt 做对照，避免多个变量混杂导致无法定位收益来源。
