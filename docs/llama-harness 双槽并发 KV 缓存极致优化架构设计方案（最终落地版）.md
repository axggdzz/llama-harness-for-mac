# llama\-harness 双槽并发 KV 缓存极致优化架构设计方案（最终落地版）

## 一、方案核心定位与设计原则

### 1\.1 硬件与环境基线

- **硬件配置**：RTX3080 20G 显存 \+ 64G 系统物理内存

- **部署架构**：双独立 llama\.cpp 进程（双物理推理槽 Slot0 / Slot1），进程完全隔离

- **核心目标**：彻底规避 KV 缓存重建、杜绝磁盘快照开销、最大化复用 GPU 显存 \+ CPU 大内存 KV 缓存，保障多业务并发推理稳定性与极致速度

### 1\.2 核心设计原则（强制落地）

1. **关闭快照驱逐**：默认禁用磁盘 Save/Restore 驱逐逻辑（`evict_snapshot_enabled = false`），全程无磁盘 IO、无缓存序列化开销

2. **业务永久槽位亲和**：四大业务固定绑定专属物理槽，首次分配后永久不漂移、不抢占

3. **内存资源拉满**：充分利用 20G 显存常驻热 KV、64G 内存溢出兜底 KV，全程内存级缓存复用

4. **强隔离高稳定**：双进程物理隔离，单业务异常不影响其他业务推理稳定性

5. **零客户端侵入**：纯代理层指纹自动识别，无需改造 Trae、WebUI、DSH 系列客户端

6. **拒绝隐性降级**：亲和槽繁忙直接返回 429 繁忙，绝不自动切换其他槽位、杜绝缓存强制重建

### 1\.3 架构分层边界（明确权责）

- **llama\.cpp 底层**：仅负责推理计算、GPU/CPU 内存 KV 缓存调度、进程级并发稳定，无业务感知、无路由逻辑

- **llama\-harness 代理层（核心自定义层）**：负责业务指纹识别、槽位亲和绑定、请求路由、槽位状态锁控、缓存保护策略

- **上层业务端**：Trae Agent、WebUI、DSH 规则引擎/主Agent，仅正常发起推理请求，无需任何定制改造

## 二、业务指纹识别体系（零侵入、高精准、零误判）

基于真实抓包指纹矩阵，构建**优先级递减、完全互斥、生产级可靠**的业务识别规则，自动生成唯一亲和 Key，用于永久槽位绑定。

### 2\.1 四大业务精准识别规则

#### 优先级1：DSH 规则引擎（最高精准，用户级永久绑定）

- 识别特征：UA 包含 `deepseek-harness` \+ 请求头携带 `x-deepseek-harness-user-id`

- 亲和 Key：`dsh_rule_{user-id}`

- 绑定粒度：单用户全局永久槽位绑定

#### 优先级2：WebUI（会话级精准绑定）

- 识别特征：请求头携带专属会话头 `X-Conversation-Id`（浏览器会话唯一 UUID）

- 亲和 Key：`webui_{conversation-id}`

- 绑定粒度：单浏览器会话独立槽位，多标签互不抢占缓存

#### 优先级3：Trae Workhertz（独家特征，绝对无碰撞）

- 识别特征：请求头携带专属标识 `x-model-provider: custom_openai_compatible`

- 亲和 Key：`trae_global`

- 绑定粒度：全局业务永久固定槽位

#### 优先级4：DSH 主Agent（兜底业务绑定）

- 识别特征：UA 包含 `deepseek-harness` \+ 携带 `X-Stainless-*` 系列请求头

- 亲和 Key：`dsh_agent_global`

- 绑定粒度：全局业务永久固定槽位

### 2\.2 未知请求兼容规则

无匹配指纹的陌生请求，走原生双槽轮询分配逻辑，不绑定永久亲和关系，完全向前兼容旧业务。

## 三、双槽亲和绑定核心机制（无缓存重建核心）

### 3\.1 核心绑定逻辑

1. **首次请求分配**：新业务/新会话首次请求，自动分配空闲物理槽位，建立 `亲和Key → SlotID` 永久映射

2. **永久锁死不漂移**：映射建立后，无论槽位空闲/繁忙，该业务后续所有请求强制路由绑定槽位

3. **槽位繁忙策略**：绑定亲和槽处于 BUSY 状态时，直接返回 429 繁忙错误，**绝不跨槽路由**，彻底杜绝跨槽缓存重建

4. **槽位释放规则**：推理完成后仅释放槽位占用状态，**永久保留亲和绑定关系**，持续复用该槽位 GPU\+CPU KV 缓存

### 3\.2 最终业务槽位稳态（最优预期）

- **Slot0**：固定常驻 Trae Agent 全局业务，长期累积编码场景上下文 KV 缓存

- **Slot1**：承载 WebUI 多会话、DSH 规则引擎、DSH 主Agent 业务，会话隔离、缓存独立

- **零缓存冲刷**：各业务独占专属槽资源，无互相抢占、无上下文重建、无磁盘IO开销

## 四、llama\.cpp 最优启动参数（适配20G显存\+64G内存）

最大化利用硬件资源，开启显存常驻\+内存溢出 KV 缓存，全程内存级缓存复用，禁用一切磁盘快照能力。

```bash
# Slot0 / Slot1 双进程统一最优参数
llama-server \
  -m 你的模型.gguf \
  --gpu-layers 99 \
  --cpu-kv-cache true \
  --max-cpu-kv-size 32G \
  --cache-type-k q8_0 \
  --cache-type-v q8_0 \
  --no-slots-save \
  --port 对应端口

```

### 参数说明

- `--gpu-layers 99`：全量模型层压入20G显存，最大化显存推理速度

- `--cpu-kv-cache true`：显存KV占满后，自动溢出至64G系统内存，内存级兜底缓存

- `--max-cpu-kv-size 32G`：限制内存KV上限，预留系统与服务内存，避免OOM

- `--cache-type-k/v q8_0`：KV缓存量化压缩，大幅提升缓存容量，牺牲极小精度换取超大缓存空间

- `--no-slots-save`：禁用槽位磁盘快照能力，彻底关闭磁盘IO开销，贴合方案核心

## 六、核心流程闭环（完整请求链路）

1. 客户端（Trae/WebUI/DSH）发起 `/v1/chat/completions` 推理请求

2. harness 代理层拦截请求，解析请求头，通过指纹规则识别业务，生成唯一亲和Key

3. SlotManager 查询亲和映射：


    - 已存在绑定槽位：校验槽位状态，IDLE则占用分配，BUSY则返回429繁忙

    - 无绑定槽位：分配空闲物理槽，建立永久亲和映射

4. 请求路由至绑定的 llama\.cpp 物理槽进程，使用该进程 GPU\+CPU 内存 KV 缓存推理

5. 推理成功/异常后，finally 强制释放槽位占用状态，**保留业务亲和绑定关系**

6. 后续同业务请求重复复用该槽位缓存，实现持续加速

## 七、方案优势与性能收益

### 7\.1 核心优势

- **极致性能**：全程内存级KV缓存复用，无磁盘序列化、无IO抖动、无缓存重建耗时

- **资源最大化**：20G显存常驻热缓存、32G内存兜底溢出缓存，64G硬件资源完全利用

- **逻辑极简低风险**：关闭复杂快照驱逐逻辑，核心链路清晰，无隐性BUG

### 7\.2 对比传统方案收益

- 优于磁盘快照驱逐：消除75ms\~23s快照恢复耗时，纯内存毫秒级缓存命中

- 优于单进程架构：保留双进程故障隔离能力，不牺牲稳定性换性能
