## 1. 背景与现状

LlamaHarness 网关在 llama-server 启动后表现为 **"首次请求明显慢、后续请求很快"**。本方案针对"首次请求慢"给出根因分析与分级优化方案，原则是 **不靠砍上下文牺牲理解能力、本地化优先、不破坏现有 KV 复用 / 槽位亲和 / 崩溃恢复机制**。

### 1.1 现象（实测日志）

| 维度       | 首次请求                                  | 后续请求                                      |
| ---------- | ----------------------------------------- | --------------------------------------------- |
| prefill    | ~173K token / 304.8s（5 min），吞吐 1160→570 tok/s 衰减 | 仅 delta（280-935 token，~1s）                |
| decode     | 63 token / 4163ms（14.89 tok/s）          | 44-50 tok/s                                   |
| graphs reused | 62                                        | 1740-2080                                     |
| draft acc  | —                                         | 0.94-0.99（draft-mtp 工作良好）               |
| restore    | 启动后有 `[KV-RESTORE] trae_global → slot0` | 会话内 LCP 复用命中（f_sim_best 0.995, f_keep 1.000） |
| 实际命中   | ❌ restore 后 task1 仍从 4K 全量 prefill | ✅ 只 prefill delta                          |

### 1.2 关键观察

- 启动后**已有** restore（日志 `[KV-RESTORE] trae_global → slot0（2.0s，跳过全量 prefill）`），但 task1 紧接着**仍全量 prefill 173K** → **restore 未命中**。
- 后续请求快是 **KV 复用（delta prefill）** 的功劳，不是 graphs 的功劳。
- wrapper 的 `[KV-MISS] 全量重算` 判定过敏感——实际底层 prompt caching 仍复用稳定前缀（看 prompt eval 仅几百 token 即证）。

## 2. 根因分析

### 2.1 根因矩阵

| #   | 根因                                          | 证据                                            | 影响          | 主因     |
| --- | --------------------------------------------- | ----------------------------------------------- | ------------- | -------- |
| R1  | 首请求 prefill 全量 ~173K token，算力硬成本   | print_timing 173734 token / 304.8s              | 5 min 主体    | ✅ 主因  |
| R2  | KV-RESTORE 未命中，无前缀复用                  | restore 后 task1 仍从 4K 全量 prefill          | 失去秒级可能  | ✅ 主因（可修） |
| R3  | 吞吐随 context 衰减（O(n²) attention + q4_0 KV 反量化） | 1160→570 tok/s 曲线                             | 放大 R1       | 中       |
| R4  | 首次 graph 复用低                              | graphs reused=62（170 chunk 才 62）             | 边际          | 低       |
| R5  | draft-mtp 首 prefill 开销                      | issue #27428（多 GPU 减半，单 GPU 影响小）       | 中（但 decode 收益正） | 低（保留） |

### 2.2 为什么"预热 graphs"治不了首次慢

这是本方案需要先澄清的关键误区：

1. **首次 5 分钟是 prefill 算力（matmul + attention），不是 graph 捕获开销。** graphs 只省 per-step kernel launch 的**开销**（μs 级），省不掉 27B 每层算力（ms 级）。即使 graph 全预捕获，173K 前向算力依旧，顶多省个位数 %。
2. **吞吐衰减曲线（1160→570）是 attention O(n²) 随 KV 增长的特征**，不是 graph-capture 特征。graph 复用不改变这条曲线。
3. **`graphs reused=62` 配 63 个 decode token** → 说明 graph 主要服务 decode，**prefill 那段根本没走 graph**（170 个 chunk 才 62 复用）。所以预热 graph 也加不到 prefill 上。

> 结论：预加载 graph 收益边际；真正让"后面快"的是 **KV 复用（delta prefill）**，不是 graphs。要救首次慢，该预加载的是 **"真实前缀的 KV"**。

## 3. 优化方案（按优先级）

### P0：修复 KV-RESTORE 前缀命中（银弹，零理解损失）🔴

**目标**：让启动后 restore 真正命中，首请求只 prefill 增量。

**根因**：§4.3 启动后对 `trae_global` restore，但存档 .bin 的 token 序列 ≠ task1 prompt 前缀 → llama-server 丢弃重算。

**方案**：

1. **存档时机**：在首次真实 prefill **完成后**立即 `KvCacheManager.SaveAsync(key, slot)`，确保存档 = task1 真实 prompt 的 token 序列。
2. **前缀稳定化**：`trae_global` 头部若有动态内容（时间戳 / 文件列表 / 会话 ID），移到**尾部**，头部只留稳定段 → restore 命中稳定头，只 prefill 动态尾（几百 token）。
3. **诊断工具（新增）**：restore 后、task1 进入时，调后端 `/v1/tokenize` 把存档序列与 task1 prompt 序列 diff，定位首个不一致位。
4. **命中判定**：观察 llama-server 日志 task1 `prompt processing` 起始 `n_tokens`——命中时起步即高位（如从 ~170K 起，仅补增量），未命中时从 4K 起全量。

**改动点**：
- `KvCacheManager`：save 时机移到首 prefill 完成后。
- `SmartScheduler`：restore 后增加 token 序列 diff 诊断（仅诊断期开启）。
- Trae 侧 prompt 结构 / 网关注入侧：头部去动态化。

**预期收益**：首次 prefill 173K → 增量（几百~几千 token），5 min → 秒级。
**风险**：prefix 漂移致偶尔 miss → 依赖现有 `[KV-MISS]` 监控 + 全量 prefill 兜底（既有逻辑已兜底）。
**回退**：restore 本就是 §4.3 既有能力，修命中不引入新风险。

---

### P1：prefill 吞吐调优（缩短全量 prefill 时间）🟠

**目标**：把 570 tok/s 的全量 prefill 吞吐拉到 ~1160+ 上限，5 min → ~2.5 min（P0 未命中时的兜底速度）。

**方案**：

1. `--ubatch-size 1024 → 2048/4096`：单步并行度↑，直接抬 tok/s（VRAM 允许）。参考 NVIDIA Qwen3.6-27B 262K-ctx 例用 4096。
2. `--batch-size 2048 → 8192/16384`：prompt processing 批量。
3. `--cache-type-k/v q4_0 → q8_0`：长 context attention 反复读 KV，`q4_0` 反量化开销大，是吞吐越往后越崩的原因之一；`q8_0` 访问快。VRAM 够用 `f16` 最快。
4. **VRAM 预算核算**：27B 3.7bpw ≈ 12.4GB 权重 + KV。`q8_0` KV @ 大 ctx 比 `q4_0` 大约翻倍，需核算 fit，可能需配合 P4 降 `-c`。

**改动点**：`LlamaFinder.BuildArgs` / `config.json`。
**预期收益**：全量 prefill 时间减半。
**验证**：print_timing 的 prompt eval tok/s↑、衰减曲线变缓。

---

### P2：上下文组织——codebase 检索替代全量 dump（治本）🟡

**目标**：把每次请求 prefill 量从 173K 降到 10-30K，根治首请求慢 + decode 慢。

**现状**：`trae_global` 首请求 dump 全库 ~173K（这是 R1 主因的源头）。

**方案**：

- **Trae 内开 codebase 索引（@Codebase）**，按需检索注入而非整库 dump。
  - ⚠️ **Trae 自带 codebase 索引默认云端**（代码临时上传算 embedding，明文删但 embedding/元数据保留）——与本地化诉求冲突。
- **全本地替代**：
  - 本地 embedding（如 `bge-m3`）+ 本地向量库（`LanceDB`/`Chroma`），检索结果 `@文件` 注入；
  - 或换 `Kilo Code` / `Continue.dev` / `Cline`（支持 Ollama 本地 embedding + 本地向量库），生成仍指向 `127.0.0.1:8081` 的 llama-server。
- **前缀稳定层**（system prompt + 项目地图 + 常驻核心文件）用 P0 的 restore 持久化。

**预期收益**：prefill 173K → 10-30K，5min → 几秒；decode 15 → 30+ tok/s；隐私全本地。
**与 P0/P1 正交**：可叠加。P0 解决"稳定前缀复用"，P2 解决"变动部分别全量"。

---

### P3：启动期 warmup 注入（架构清晰化 + graph bonus）🟢

**目标**：启动→首请求之间插入 warmup 阶段，eager restore + 可选 graph 预捕获。

**注入点**：`SmartScheduler.WakeUpAsync`，`WaitReady` 成功后、置 `Running` 前加 `WarmupAsync`，`Waking` 态 hold 住首请求。

**方案**：

1. **eager restore**：对 `AutoPreemptiveApps`（`trae_global` / `dsh_agent_global`）绑定的 key 主动 `RestoreAsync`（已在做，重点是 P0 命中）。
2. **可选 graph 预热**：restore 命中后 POST 一个 `max_tokens=1` 的 dummy 捕获 decode graph（边际收益，免费）。
3. **状态机**：`Waking` 子阶段延展至 warmup 完成再转 `Running`。

**改动点**：`SmartScheduler` 新增 `WarmupAsync` + `Waking` 子阶段。
**预期收益**：边际（decode graph），主要是把 restore 时机/命中显式化、可观测。
**风险**：warmup 占用首请求前的时间窗（restore 命中时 ~2s，可接受；未命中走全量）。

### P4：配置参数复盘 🟢

| 参数                | 现值     | 建议              | 理由                                                                 |
| ------------------- | -------- | ----------------- | -------------------------------------------------------------------- |

## 6. 验证方法

- **关键指标**：

  - task1 `prompt processing` 起始 `n_tokens`（判断 restore 命中：命中时起步即高位）；

## 7. restore 命中率可观测指标设计

> 本节是架构的 **North Star metric**：把 restore 命中率从不可见变为可观测、可对账、可告警。它直接决定 §3 P0（首请求秒级）是否落地——命中率上不去，整套"秒级首请求"就是空中楼阁。

### 7.1 设计目标

- **可观测**：命中/未命中计数 + 持久化 + 趋势展示。
- **可对账**：判定逻辑以 **llama-server 自身日志为准**，消除 wrapper `[KV-MISS]` 误报（实测：报"全量重算"但 prompt eval 仅几百 token）。
- **可告警**：命中率跌破阈值 → UI 黄/红提示，驱动 §3 P0 修 prefix。

### 7.2 真值源：弃用轻量指纹，以 llama-server 日志为准

现状（§4.6）用"轻量指纹（条数 + role|content 长度）"判 `[KV-HIT]/[KV-MISS]`。问题：**长度一样 ≠ token 序列一样**，且实测与底层 prompt caching 判定不一致。

**真值源 = llama-server `print_timing`**：

- restore **命中** ⟺ 该 key 首请求 `prompt processing` **起始 `n_tokens` ≈ 已存档量**（仅 prefill 增量，几百~几千 token）。
- restore **未命中** ⟺ 起始 `n_tokens` 从低位（0 / 4K）起，最终 ≈ 全量 prompt（数万~十几万 token）。

> 即：以 llama-server 日志为 ground truth，wrapper 指纹降级为辅助预判，仅供 7.5 对账。

### 7.3 判定流程（一次"唤醒→首请求" = 一个样本）

```text
唤醒周期开始
  1. harness 对 key 执行 RestoreAsync          → 记 attempt++（per-key）
  2. 该 key 首个真实请求到达                     → 记 task id（绑定本次 attempt）
  3. LlamaStatsParser 抓该 task 的 print_timing：
       start_n = prompt processing 第一条 n_tokens
       end_n   = prompt processing 最终 n_tokens（= 该请求总 prompt 量）
       saved_n = kv_cache_index.json 中该 key 的 nTokens
  4. 判定：
       hit   := start_n >= saved_n * 0.9  且  (end_n - start_n) <= Δ阈值(如 4096)
       miss  := start_n <= 起步阈值(如 8192) 且 end_n ≈ 全量
       否则  := ambiguous（保守算 miss）
  5. 回填：RestoreStats.Record(key, hit/miss, start_n, end_n, saved_n, Δ)
  6. 交叉验证：读 wrapper 本次的 [KV-HIT]/[KV-MISS] 预判 → 记 false_miss/false_hit
```

### 7.4 指标定义

| 指标 | 含义 |
|------|------|
| `restore_attempts_total` | 唤醒 restore 总次数 |
| `restore_hits_total` / `restore_misses_total` | 命中 / 未命中次数 |
| `restore_hit_rate` | hits / attempts（核心 North Star） |
| `restore_false_miss_rate` | wrapper 报 MISS 但实际命中 / attempts（指纹误报率，应趋近 0） |
| `restore_false_hit_rate` | wrapper 报 HIT 但实际未命中 / attempts |
| `avg_delta_prefill_tokens` | 命中时增量 prefill 均值（越低越好） |
| `avg_full_prefill_ms` | 未命中时全量 prefill 均值（量化损失） |
| per-key 命中率 | `trae_global` / `dsh_agent_global` 分别统计 |

### 7.5 与 llama-server 日志对齐的判定真值表

| wrapper 预判 | start_n（起始） | end_n − start_n（增量） | 真实命中 | 计入 |
| --- | --- | --- | --- | --- |
| HIT  | 高位（≈ saved_n） | 小（≤ Δ阈值） | ✅ 命中 | hits |
| HIT  | 低位 | ≈ 全量 | ❌ 误报 HIT | false_hit + misses |
| MISS | 高位 | 小 | ✅ 实际命中（wrapper 误报） | hits + false_miss |
| MISS | 低位 | ≈ 全量 | ❌ 未命中 | misses |

### 7.6 落盘与展示

- **持久化**：`config/restore_stats.json`（per-key → `{attempts, hits, misses, false_miss, false_hit, last_hit_at, last_delta_n, last_full_ms}`），原子写（复用 AppConfig 模式）。
- **展示**：系统资源页 / 槽位管理页加「restore 命中率」卡片——总命中率 + per-key + 误报率 + 最近一次命中/未命中明细。
- **告警**：`restore_hit_rate < 80%`（可配）→ 卡片黄；`< 50%` → 红，并在 warn_error.log 落一条。
- **slot.log**：每次 restore 补一行 `[KV-RESTORE-JUDGE] key=trae_global hit=1 start_n=171234 end_n=171890 saved_n=171200 delta=656`（与 §4 可观测标记体系统一）。

### 7.7 改动点

| 模块 | 改动 |
|------|------|
| `LlamaStatsParser` | 暴露 `GetPromptProcessing(taskId) → (start_n, end_n)`（按 task ID 归组，已有能力，补查询接口） |
| `KvCacheManager` | restore 时把 `saved_n`（kv_cache_index.json 的 nTokens）透传给判定流程 |
| `SmartScheduler` | 唤醒→首请求周期：restore 后记 attempt；首请求 task 完成后用 parser 结果回填 hit/miss |
| 新增 `RestoreStats` | 计数 + 持久化 + 查询 + 告警阈值（静态类，内部锁，复用 LogFile 模式） |
| wrapper 指纹判定 | 降级为预判（保留 `[KV-HIT]/[KV-MISS]` 日志，仅供 7.5 对账，不再作命中真值） |

### 7.8 验收准则

- `restore_false_miss_rate + restore_false_hit_rate` 趋近 0（判定与 llama-server 日志一致）。
- `restore_hit_rate` 持续可观测；命中时 `avg_delta_prefill_tokens < Δ阈值`（如 4096）。
- 未命中事件在 UI / warn_error.log 显式暴露，驱动 §3 P0 修 prefix。

## 8. 可实施 C# 接口签名

本节把 §7（命中率可观测）和 §3 P0（前缀诊断）落成可直接落地的 C# 契约。按现有架构约束写：.NET 8、**零第三方依赖（仅 BCL）**、异步 I/O + 纯函数判定分离、内部锁串行化。三块可独立合并、独立回退。

### 8.1 设计约束

| 约束 | 决策 |
|------|------|
| 零第三方依赖 | 仅用 `System.Text.Json` / `System.Net.Http` / `System.Threading` |
| JSON 类型 | `JsonNode`（`System.Text.Json.Nodes`），与 TokenGuard 既有路径一致 |
| 线程模型 | 解析在进程输出线程；判定为纯函数；计数静态类 + 内部锁 |
| 命名约定 | 复用既有风格：`XxxAsync` / `SaveAsync(key, slot)` / `RestoreAsync(key, slot)` |
| 判定与 IO 分离 | `RestoreJudger.Judge()` 纯函数可单测；IO 全藏在接口后 |
| 热路径零新增开销 | `requestTokens` 复用 TokenGuard 已算出的值；diff 诊断仅离线调用 |

### 8.2 块一：时序查询接口（§7.7 第一行落地）

现有 `LlamaStatsParser` 已按 task ID 归组、50 轮环形缓冲、内部锁串行化，缺的是**按 task 取结果**的查询入口。补两个方法即可，不动 `Feed` / `Reset` / `RoundUpdated` 既有语义。

```csharp
namespace LlamaHarness.Scheduling.Stats;

/// <summary>
/// 单个 task 的 print_timing 解析结果。所有字段来自 llama-server 自身日志，
/// 是 restore 命中判定的 ground truth（§7.2）。字段名与 print_timing 原文对齐，便于对账。
/// </summary>
```

### 8.3 块二：判定逻辑（§7.3 步骤 4，纯函数可单测）

判定与 IO 彻底分离：`RestoreJudger.Judge()` 无锁、无 IO、无状态，任何输入组合都能单测覆盖。

```csharp
namespace LlamaHarness.Scheduling.Restore;

/// <summary>命中判定阈值。全部可配，默认值取 §7.3。</summary>
public sealed record JudgementThresholds
{
    /// <summary>命中上限：PromptEvalTokens ≤ 该值即判命中。默认 4096 = §7.3 Δ阈值。</summary>
    public long MaxDeltaTokens { get; init; } = 4096;

    /// <summary>未命中下限：PromptEvalTokens ≥ requestTokens × 该比例即判未命中。默认 0.5。</summary>
    public double FullRatio { get; init; } = 0.5;

    /// <summary>介于两者之间 → ambiguous，保守算 miss（默认 true）。</summary>
    public bool AmbiguousCountsAsMiss { get; init; } = true;
}

public enum RestoreJudgementReason
{
    HitByDelta,        // 增量 prefill 很小 → 命中
    MissByDelta,       // prefill ≈ 全量 → 未命中
    Ambiguous,         // 介于阈值之间，保守算 miss
    NoTimingAvailable, // 该 task 未解析到 print_timing（日志缺失 / 超时）
}

public sealed record RestoreJudgement
{
    public string Key { get; init; } = "";
    public int TaskId { get; init; }
    public bool Hit { get; init; }
    public RestoreJudgementReason Reason { get; init; }

    public long PromptEvalTokens { get; init; }   // timing.PromptEvalTokens
    public long RequestTokens { get; init; }       // TokenGuard 已算出的请求 messages token 数
    public long SavedN { get; init; }              // kv_cache_index.json 该 key 的 nTokens
    public long DeltaPrefillTokens { get; init; }  // = PromptEvalTokens（命中时应 ≤ MaxDeltaTokens）

    /// <summary>wrapper 的轻量指纹预判（现有 [KV-HIT]/[KV-MISS]）。</summary>
    public bool WrapperPredictedHit { get; init; }

    /// <summary>wrapper 报 MISS 但实际命中（§7.4 false_miss）。</summary>
    public bool FalseMiss => !WrapperPredictedHit && Hit;
    /// <summary>wrapper 报 HIT 但实际未命中（§7.4 false_hit）。</summary>
    public bool FalseHit => WrapperPredictedHit && !Hit;
}

/// <summary>
/// 纯函数判定器。无 IO、无锁、无状态，便于单测覆盖。
/// </summary>
public static class RestoreJudger
{
    public static RestoreJudgement Judge(
        string key,
        int taskId,
        TaskTiming? timing,
        long requestTokens,
        long savedN,
        bool wrapperPredictedHit,
        JudgementThresholds? th = null)
    {
        th ??= new JudgementThresholds();
        var j = new RestoreJudgement
        {
            Key = key,
            TaskId = taskId,
            WrapperPredictedHit = wrapperPredictedHit,
            RequestTokens = requestTokens,
            SavedN = savedN,
        };

        // 无数据一律保守算 miss —— 避免"误判命中"掩盖真实的 restore 失效。
        if (timing is null || !timing.IsComplete)
        {
            j.Hit = false;
            j.Reason = RestoreJudgementReason.NoTimingAvailable;
            return j;
        }

        j.PromptEvalTokens = timing.PromptEvalTokens;
        j.DeltaPrefillTokens = timing.PromptEvalTokens;

        if (timing.PromptEvalTokens <= th.MaxDeltaTokens)
        {
            j.Hit = true;
            j.Reason = RestoreJudgementReason.HitByDelta;
        }
        else if (timing.PromptEvalTokens >= (long)(requestTokens * th.FullRatio))
        {
            j.Hit = false;
            j.Reason = RestoreJudgementReason.MissByDelta;
        }
        else
        {
            j.Hit = !th.AmbiguousCountsAsMiss;
            j.Reason = RestoreJudgementReason.Ambiguous;
        }
        return j;
    }
}
```

```csharp
    /// <summary>
    /// 对存档序列与本次首请求序列做 token 级 diff，定位首个不一致位。
    /// 仅诊断期开启，不在热路径调用（§7.7 wrapper 已降级为预判）。
    /// </summary>
    Task<TokenDiffResult?> DiagnoseAsync(string key, JsonNode requestMessages,
        CancellationToken ct = default);
}

/// <summary>IPrefixDiffDiagnoser 默认实现骨架。</summary>
internal sealed class PrefixDiffDiagnoser : IPrefixDiffDiagnoser
{
    private readonly ISavedPrefixStore _saved;
    private readonly IChatTokenizer _tok;

    public PrefixDiffDiagnoser(ISavedPrefixStore saved, IChatTokenizer tok)
    { _saved = saved; _tok = tok; }

    public async Task<TokenDiffResult?> DiagnoseAsync(
        string key, JsonNode requestMessages, CancellationToken ct = default)
    {
        var savedTokens = await _saved.LoadAsync(key, ct);
        if (savedTokens is null || savedTokens.Length == 0) return null;

        var req = await _tok.TokenizeMessagesAsync(requestMessages, ct);
        if (req is null || req.Tokens.Length == 0) return null;

        // 最长一致前缀
        var limit = Math.Min(savedTokens.Length, req.Tokens.Length);
        long common = 0;
        for (long i = 0; i < limit; i++)
        {
            if (savedTokens[i] != req.Tokens[i]) break;
            common++;
        }

        bool exactPrefix = savedTokens.Length <= req.Tokens.Length && common == savedTokens.Length;
        long? divergence = exactPrefix ? null : Math.Min(common, limit);

        return new TokenDiffResult
        {
            CommonPrefixTokens = common,
            SavedTokens = savedTokens.Length,
            RequestTokens = req.Tokens.Length,
            FirstDivergenceTokenIndex = divergence,
            DivergenceMessageIndex = MapTokenToMessage(req, common),
            SavedTokenWindow = Window(savedTokens, common),
            RequestTokenWindow = Window(req.Tokens, common),
            SavedIsExactPrefix = exactPrefix,
        };
    }

    /// <summary>token 下标 → message 下标（在 MessageStartToken 上二分）。</summary>
    private static int? MapTokenToMessage(TokenizedPrompt p, long tokenIndex)
    {
        int lo = 0, hi = p.MessageStartToken.Length - 1, ans = -1;
        while (lo <= hi)
        {
            var mid = (lo + hi) / 2;
            if (p.MessageStartToken[mid] <= tokenIndex) { ans = mid; lo = mid + 1; }
            else hi = mid - 1;
        }
        return ans >= 0 ? ans : null;
    }

    /// <summary>分歧点附近 token 窗口（前 4 后 8，截断到边界）。</summary>
    private static long[]? Window(long[] tokens, long pos, int before = 4, int after = 8)
    {
        if (pos < 0 || pos > tokens.Length) return null;
        var lo = Math.Max(0, pos - before);
        var hi = Math.Min(tokens.Length, pos + after);
        var window = new long[hi - lo];
        Array.Copy(tokens, lo, window, 0, hi - lo);
        return window;
    }
}
```

```csharp
private async Task RecordRestoreJudgementAsync(string key, int taskId, bool wrapperPredictedHit)
{
    if (!_restoredKeysThisRun.Contains(key)) return;       // 本次唤醒未 restore 该 key → 不计

    // 等该 task 的 total time 行（最多 5s，避免日志延迟拖垮回填）

        timeout: TimeSpan.FromSeconds(5), CancellationToken.None);

    // requestTokens 复用 TokenGuard 已算出的值 —— 热路径零额外 tokenize
    var j = RestoreJudger.Judge(
        key: key,
        taskId: taskId,
        timing: timing,
        requestTokens: _tokenGuard.LastRequestTokenCount,
        savedN: _savedPrefix.TokenCount(key) ?? 0,
        wrapperPredictedHit: wrapperPredictedHit);

    RestoreStats.OnJudgement(j);

    // 与 §4 可观测标记体系统一，落 slot.log
    _log.SlotAppend($"[KV-RESTORE-JUDGE] key={key} hit={j.Hit ? 1 : 0} " +
                    $"reason={j.Reason} prompt_eval_tokens={j.DeltaPrefillTokens} " +
                    $"request_tokens={j.RequestTokens} saved_n={j.SavedN} " +
                    $"wrapper_hit={j.WrapperPredictedHit ? 1 : 0} " +
                    $"false_miss={j.FalseMiss} false_hit={j.FalseHit}");

    if (RestoreStats.ShouldWarn(RestoreStats.Snapshot()))
        _log.Warn($"[KV-RESTORE-WARN] restore 命中率跌破阈值，见 UI 卡片");

    _restoredKeysThisRun.Remove(key);                      // 本 key 本次唤醒已回填
}
```

### 8.7 单测建议（映射到 LlamaHarness.Tests）

纯函数优先覆盖，IO 全部走接口 mock：

1. **`RestoreJudger.Judge` 判定矩阵**（§7.5 四象限 + 边界）：
   - `PromptEvalTokens=100, MaxDelta=4096` → `HitByDelta`
   - `PromptEvalTokens=100000, requestTokens=173000, FullRatio=0.5` → `MissByDelta`
   - `PromptEvalTokens=8000, requestTokens=173000` → `Ambiguous`（保守算 miss）
   - `timing=null` / `!IsComplete` → `NoTimingAvailable`
   - wrapper 报 MISS + 实际命中 → `FalseMiss=true`；wrapper 报 HIT + 实际未命中 → `FalseHit=true`
2. **`PrefixDiffDiagnoser`**：
   - 存档为请求严格前缀 → `SavedIsExactPrefix=true`，`FirstDivergenceTokenIndex=null`
   - 中间分歧 → `FirstDivergenceTokenIndex` 精确、`DivergenceMessageIndex` 正确映射
   - 存档更长（请求是存档前缀）→ `FirstDivergenceTokenIndex=requestLen`
   - `LoadAsync` 返回 null → 整体返回 null（降级）
3. **`RestoreStats`**：计数累加、`HitRate`/`FalseRate` 计算、`ShouldWarn` 双阈值、持久化原子写（写失败不抛）
4. **`LlamaStatsParser`**：喂真实 print_timing 文本块，验证 `TaskTiming` 各字段、`IsComplete` 翻转、`WaitPromptProcessingAsync` 超时返回 null

### 9.2 不建议的方向

- ❌ **删 draft-mtp**：decode 会从 44-50 跌回 ~15 tok/s，得不偿失。
- ❌ **预加载 graphs 期待解决首次慢**：瓶颈是 prefill 算力 + KV 未命中，非 graph 开销。
- ❌ **单纯砍上下文**：伤理解；应改组织方式（P2）而非截断。
